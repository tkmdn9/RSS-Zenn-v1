# 要件定義書

## はじめに

Zenn Article Dashboardは、複数のZenn RSSフィードから記事を集約し、トピック別に整理して表示するWebダッシュボードです。ユーザーは関心のあるトピック（Claude Code、Skills、MCP、RAG）の最新記事を一箇所で閲覧でき、既読管理やフィルタリング機能を通じて効率的に情報収集できます。

本システムは、ミニマリストデザインとトピック別カラーコーディングを採用し、Next.js Server Componentsを活用したサーバーサイドレンダリングにより高速な初期表示を実現します。

## 用語集

- **Dashboard**: Zenn記事を表示するメインのWebアプリケーション画面
- **Article_Fetcher**: サーバーサイドでZenn RSSフィードから記事データを取得するコンポーネント
- **Article_Normalizer**: 取得した記事データを統一フォーマットに変換するコンポーネント
- **Article_Sorter**: 記事を公開日時順にソートするコンポーネント
- **Filter_Bar**: ユーザーがトピックでフィルタリングするためのUIコンポーネント
- **Article_Grid**: 記事カードを格子状に表示するUIコンポーネント
- **Topic**: 記事のカテゴリ（claudecode, skills, mcp, rag）
- **Read_Status_Manager**: ブラウザのlocalStorageを使用して既読状態を管理するコンポーネント
- **Skeleton_Loader**: データ読み込み中に表示するプレースホルダーUI
- **ZennArticle**: 正規化された記事データオブジェクト（id, title, link, pubDate, author, topic, thumbnail）
- **TopicType**: トピックの型定義（'claudecode' | 'skills' | 'mcp' | 'rag'）

## 要件

### 要件1: RSSフィードデータの取得

**ユーザーストーリー:** ユーザーとして、複数のZenn RSSフィードから記事を取得してほしい。そうすれば、異なるトピックのコンテンツを集約して閲覧できる。

#### 受入基準

1. Article_Fetcherは、NEXT_PUBLIC_TOPICS環境変数で指定されたRSSフィードから記事を取得しなければならない
2. RSSフィードが利用できない場合、Article_Fetcherはエラーをログに記録し、他のフィードからの取得を継続しなければならない
3. Article_Fetcherは、Next.js Server Componentsを使用してサーバーサイドで実行されなければならない
4. 取得が完了した場合、Article_Fetcherは生の記事データをArticle_Normalizerに返さなければならない
5. Article_Fetcherは、rss-parserライブラリを使用してRSSフィードのXMLを解析しなければならない

### 要件2: 記事データの正規化

**ユーザーストーリー:** 開発者として、記事データを一貫したフォーマットに正規化してほしい。そうすれば、UIが異なるソースからの情報を確実に表示できる。

#### 受入基準

1. Article_Normalizerは、生のRSSデータをZennArticleオブジェクトに変換しなければならない
2. Article_Normalizerは、各RSSアイテムからid、title、link、pubDate、author、thumbnailを抽出しなければならない
3. Article_Normalizerは、ソースフィードに基づいて正しいTopic値を割り当てなければならない
4. 必須フィールドが欠落している場合、Article_Normalizerはデフォルト値を使用しなければならない（オプションフィールドは空文字列）
5. Article_Normalizerは、すべてのpubDate値が有効なISO 8601日付文字列であることを保証しなければならない

### 要件3: 記事のソート

**ユーザーストーリー:** ユーザーとして、最新の記事を最初に表示してほしい。そうすれば、最新のコンテンツを常に把握できる。

#### 受入基準

1. Article_Sorterは、記事をpubDateの降順（新しい順）でソートしなければならない
2. Article_Sorterは、日付比較にdate-fnsライブラリを使用しなければならない
3. 2つの記事が同じpubDateを持つ場合、Article_Sorterはソースフィードからの相対的な順序を維持しなければならない

### 要件4: トピックベースのフィルタリング

**ユーザーストーリー:** ユーザーとして、トピックで記事をフィルタリングしたい。そうすれば、自分の興味に関連するコンテンツに集中できる。

#### 受入基準

1. Filter_Barは、利用可能なすべてのトピック（claudecode、skills、mcp、rag）のフィルタオプションを表示しなければならない
2. ユーザーがトピックフィルタを選択した場合、Dashboardはそのトピックに一致する記事のみを表示しなければならない
3. フィルタが選択されていない場合、Dashboardはすべてのトピックの記事を表示しなければならない
4. Filter_Barは、複数のトピックを同時に選択できるようにしなければならない
5. Filter_Barは、現在アクティブなフィルタを視覚的に示さなければならない

### 要件5: トピック別カラーコーディング

**ユーザーストーリー:** ユーザーとして、トピックを色で視覚的に区別したい。そうすれば、記事のカテゴリを素早く識別できる。

#### 受入基準

1. Article_Gridは、Claude Code記事を紫色のカラーコーディングで表示しなければならない
2. Article_Gridは、Skills記事を黄色のカラーコーディングで表示しなければならない
3. Article_Gridは、MCP記事を青色のカラーコーディングで表示しなければならない
4. Article_Gridは、RAG記事を緑色のカラーコーディングで表示しなければならない
5. Dashboardは、すべてのUI要素（バッジ、ボーダー、背景）でカラーコーディングを一貫して適用しなければならない

### 要件6: 記事の表示

**ユーザーストーリー:** ユーザーとして、記事情報を明確なグリッドレイアウトで見たい。そうすれば、複数の記事を効率的に閲覧できる。

#### 受入基準

1. Article_Gridは、記事をレスポンシブなグリッドレイアウトで表示しなければならない
2. Article_Gridは、各記事のタイトル、著者、公開日、トピック、サムネイルを表示しなければならない
3. ユーザーが記事をクリックした場合、Dashboardは記事リンクを新しいブラウザタブで開かなければならない
4. Article_Gridは、スタイリングにTailwind CSSを使用しなければならない
5. Article_Gridは、ビューポート幅に基づいて列数を調整しなければならない（レスポンシブデザイン）

### 要件7: 既読状態の管理

**ユーザーストーリー:** ユーザーとして、どの記事を読んだかをシステムに記憶してほしい。そうすれば、新しいコンテンツと閲覧済みコンテンツを区別できる。

#### 受入基準

1. ユーザーが記事リンクをクリックした場合、Read_Status_Managerはその記事を既読としてマークしなければならない
2. Read_Status_Managerは、既読状態をブラウザのlocalStorageに保存しなければならない
3. Read_Status_Managerは、ブラウザセッションをまたいで既読状態を永続化しなければならない
4. Article_Gridは、既読記事と未読記事を視覚的に区別しなければならない（例：透明度、バッジ、テキストスタイル）
5. Read_Status_Managerは、既読状態の追跡に記事idを一意の識別子として使用しなければならない

### 要件8: ローディング状態の表示

**ユーザーストーリー:** ユーザーとして、記事を取得している間はローディングインジケータを表示してほしい。そうすれば、システムが動作していることがわかる。

#### 受入基準

1. 記事を取得している間、DashboardはSkeleton_Loaderを表示しなければならない
2. Skeleton_Loaderは、Article_Gridレイアウトに一致するプレースホルダーカードを表示しなければならない
3. 記事データが利用可能になった場合、DashboardはSkeleton_LoaderをArticle_Gridに置き換えなければならない
4. Skeleton_Loaderは、視覚的フィードバックのためにTailwind CSSアニメーションを使用しなければならない

### 要件9: APIエンドポイント

**ユーザーストーリー:** 開発者として、記事を取得するための専用APIエンドポイントが欲しい。そうすれば、クライアントがプログラム的に記事データをリクエストできる。

#### 受入基準

1. Dashboardは、GET /api/articlesエンドポイントを公開しなければならない
2. エンドポイントがGETリクエストを受信した場合、Article_Fetcherは記事を取得、正規化、ソートしなければならない
3. エンドポイントは、Content-Type application/jsonで記事をJSONとして返さなければならない
4. 取得中にエラーが発生した場合、エンドポイントは適切なHTTPエラーステータスコード（500）とエラーメッセージを返さなければならない
5. エンドポイントは、サーバーサイドでのみ実行され、RSSフィードのURLをクライアントに公開してはならない

### 要件10: 環境設定

**ユーザーストーリー:** 開発者として、環境変数を通じてRSSフィードトピックを設定したい。そうすれば、コード変更なしでデータソースを簡単に変更できる。

#### 受入基準

1. Dashboardは、NEXT_PUBLIC_TOPICS環境変数からトピック設定を読み取らなければならない
2. NEXT_PUBLIC_TOPICS変数は、name、url、typeプロパティを持つトピックオブジェクトのJSON配列を含まなければならない
3. NEXT_PUBLIC_TOPICSが定義されていない場合、Dashboardはエラーメッセージを表示しなければならない
4. Dashboardは、各トピックが有効なTopicType値（claudecode、skills、mcp、rag）を持つことを検証しなければならない
5. 無効なトピック設定が検出された場合、Dashboardは警告をログに記録し、そのトピックをスキップしなければならない

### 要件11: グローバルナビゲーション

**ユーザーストーリー:** ユーザーとして、一貫したナビゲーションバーが欲しい。そうすれば、アプリケーションのコンテキストを理解し、主要機能にアクセスできる。

#### 受入基準

1. Dashboardは、ページ上部にグローバルナビゲーションバーを表示しなければならない
2. ナビゲーションバーは、アプリケーションタイトル「Zenn Article Dashboard」を表示しなければならない
3. ナビゲーションバーは、スクロール中も表示され続けなければならない（固定配置）
4. ナビゲーションバーは、アプリケーション全体と一貫したミニマリストデザインスタイルを使用しなければならない

### 要件12: 外部リンクの処理

**ユーザーストーリー:** ユーザーとして、記事リンクを新しいタブで開いてほしい。そうすれば、ダッシュボードでの位置を失わない。

#### 受入基準

1. ユーザーが記事リンクをクリックした場合、Dashboardはリンクを新しいブラウザタブで開かなければならない
2. Dashboardは、すべての記事リンクにtarget="_blank"とrel="noopener noreferrer"を設定しなければならない
3. Dashboardは、リンクが外部で開くことを視覚的に示さなければならない（例：アイコンまたはスタイリング）
